## New in 1.3.0

- **Fixed: Blu-ray 3D from a pressed disc showed one view, squeezed to half width** (present since Blu-ray 3D
  exists in Lumen). The second view of an encrypted disc was never read: libbluray's decrypting file only
  answers reads of exactly one aligned unit (6144 bytes), and Lumen asked for 192 KiB at once. The status
  said "3D MVC", the picture was the left eye labelled as side-by-side. Unencrypted images and folders
  were not affected, which is why the tests did not show it. The jump marks of the second view were
  missing as well: pressed discs keep them in the extension data of the clip (`CPI_SS`). Checked with a
  pressed 3D disc decrypted through the store plugin *My AACS Plugin*: 2986 pictures of the first two clips,
  every one paired with its second view, the decoder delivers both views.
- **Clip changes without a hiccup.** Every clip of a Blu-ray counts its own time stamps. At each change –
  studio logo to film, seamless branching – the player saw a time jump, reset playback and lost pictures
  ("Audio/Video desynchronisation detected"). Lumen now puts all clips of a playlist on one time line
  (titles and menus played through libbluray, 2D and 3D). With the data of the same disc, picture and sound
  time stamps run through the change without a jump and the decoder reports nothing. In 3D the last picture
  of a clip is now paired with its own second view instead of one from the next clip.
- **Disc menus.** Discs start with their menu, as before, and now also when a disc, image or folder is
  opened from the command line (`--main` plays the main feature, `--menu` forces the menu).
  - **HDMV menus and subtitles decoded by libbluray are drawn.** They arrive as compressed overlays (run
    lengths with a palette); Lumen had only registered the handler for BD-J graphics, so an HDMV menu
    played without its buttons. Checked with the subtitles of a 3D sample image, which take the same path;
    an HDMV menu disc was not at hand.
  - **A menu that cannot start plays the main feature** instead of ending with "Playback failed", and the
    *Titles* page says why. This is the case for BD-J menus (most recent film discs) without a Java runtime
    or without libbluray's Java archive.
  - **BD-J:** libbluray needs `libbluray-j2se-<version>.jar` and `libbluray-awt-j2se-<version>.jar` in its
    own version. A folder `bdj` next to the program or in Lumen's data folder is now passed on to
    libbluray. **The packages do not contain the archive yet**, so BD-J menus work where the system
    provides it (Linux: the distribution's `libbluray-bdj` package) or where you add it.
- **Quitting closes the disc (macOS).** The player window turned its own close event into a second quit
  request; AppKit then ends the process on the spot. mpv, the disc and the AACS library were never closed,
  and the screen mode of an output profile was not switched back by Lumen. With MakeMKV as AACS library its
  helper process stayed behind after every quit and kept the drive busy for the next start – of Lumen and of
  MakeMKV. The teardown now runs before the windows close. If a library hangs while opening a disc, Lumen
  still ends after six seconds.
- **The window.**
  - Right side: one row of sections (*Playback, Cinema, Streaming, Output, Plugins*) and, under *Playback*,
    its pages (*Titles, Chapters, Audio, Subtitles, Picture*). Nine tabs used to wrap onto two lines.
  - The transport bar always stays in view; what is above it scrolls when the window is low.
  - Start page: three quick actions (file or image, disc folder, stream link), the two start options side by
    side, and the last error as a banner that can be closed.
  - The language moved from the start page into a menu in the header (globe symbol). The header no longer
    pushes its last buttons out of a narrow window.
- **"The drive is not responding"**: when reading the disc structure takes longer than 20 seconds, the
  *Titles* page says so and names the usual reason, another program using the disc.
- **Plugins:** an optional disc library that cannot be loaded – built for another processor (an Intel
  `libaacs.dylib` on Apple Silicon), a dependency missing – no longer switches the whole plugin off. The card
  shows the reason in one line, the rest of the plugin works. macOS: a library with the version in its name
  (`libaacs.0.dylib`) was loaded by Lumen, but libbluray then looked for `libaacs.dylib`; the name is now
  passed on as it is.

## For developers

- `tools/test_bd3d.sh` (run on every CI platform) now also checks the playlist time line: a generated M2TS
  with B-frames and sound, moved by 100 s, must carry exactly these time stamps.
- `mvcmerge_test <disc> <playlist> <out.m2ts> [seek] [max MiB]` stops after the given amount, for real
  discs. `bdoverlay_test <disc|iso> <out.png>` saves the first subtitle plane libbluray decodes.
- `LUMEN_NO_DRIVES=1` ignores the physical drives (tests with images while a disc is in the drive).

## Known limits

- BD-J menus need Java and libbluray's Java archive, see above. Without them the main feature plays.
- Blu-ray 3D in the player window was checked with two unencrypted 3D images and with the first clip of the
  pressed disc; the change to the second clip was checked on the merged stream, not in the window.
- The window changes were checked on macOS.
