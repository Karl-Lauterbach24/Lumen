## New in 1.3.1

- **Disc menus written in Java (BD-J) start on macOS and Windows.** Most recent film discs have such a menu.
  libbluray runs it in a Java VM and needs its own Java classes for that, in exactly its own version. Neither
  Homebrew nor MSYS2 ship them, so in 1.3.0 these discs went straight to the main feature. The macOS and
  Windows packages now contain the archive for the libbluray they are built with (1.5.0). What remains to be
  installed is a **Java runtime** (JRE or JDK from version 8 on, for the same processor type as Lumen).
  Without one the main feature plays, as before, and the *Titles* page says why.
- **Lumen finds the Java runtime.** libbluray uses `JAVA_HOME` and otherwise searches by itself:
  - macOS: its own search only found the old browser plug-in on the test Mac, not the installed JDK. Lumen
    now asks `/usr/libexec/java_home` and also looks at Homebrew's `openjdk`.
  - Windows: libbluray reads registry entries that newer OpenJDK installers no longer write unless asked to.
    Without them Lumen looks into the usual folders under `Program Files` (Eclipse Adoptium, Java, Microsoft,
    Zulu, BellSoft, Amazon Corretto, OpenJDK). A folder `jre` next to `lumen.exe` goes first, for a portable
    setup.
  - A `JAVA_HOME` that is already set stays as it is.
- **Linux:** the packages now name the distribution's `libbluray-bdj` (the same archive, for the libbluray of
  the distribution) – as a recommendation in the `.deb`, as a suggestion in the `.rpm`.
- A folder `bdj` in Lumen's data folder is only used when it holds the archive of the libbluray in use.
  Before, an archive of another version there kept libbluray from finding the right one elsewhere.

## For developers

- `resources/bdj/` holds the archives, `tools/build_bdj.sh <libbluray source>` builds them with javac and jar
  alone (no ant). CMake and `tools/deploy_windows.py` warn when libbluray has moved on and the archive for
  its version is missing.
- `tools/test_bdj.sh <build> <work>`: `tools/make_test_bdj.py` generates a disc with a film and a small Java
  menu over it (two buttons), `bdj_test` starts it through libbluray, presses *down* and *enter* and checks
  what the menu draws and that the film behind it plays. It rides along in `tools/test_bd3d.sh` on every CI
  platform as a report; without a JDK it skips itself.
- The Windows package builds now build and run the playlist time line check from 1.3.0 and the BD-J test.
  They only built `lumen` and `mvcmerge_test`, so on Windows both were skipped – the 1.3.0 notes said the
  time line check ran on every CI platform, which was true for Linux and macOS only. It passes on Windows.
- `LUMEN_PLAYER_SNAPSHOT=shot.png@+8` saves the player window 8 seconds after the program started, without
  pausing (disc menus count their time per playlist).

## Checked, and known limits

- The generated disc with its Java menu runs through libbluray with the shipped archive on every platform
  the package builds can try it on: macOS on Apple Silicon and on Intel (Java 21), Windows x64 (Java 17) and
  Windows ARM64 (Java 21). On a Mac here also with Java 8 and Java 17, and in the player window: the menu is
  drawn over the running film, *down* and *enter* reach it.
- **Not checked with a pressed BD-J disc yet.** Such menus are large programs; libbluray runs many of them,
  not all. A menu that does not come up can be left with *Main feature* on the *Titles* page, or skipped
  from the start with `--main` or by switching off *Start with disc menu*.
- The Linux build containers have no JDK, so the test skips itself there. Linux uses the distribution's
  libbluray and archive.
- The search for Java in the folders under `Program Files` was not tried on a Windows computer: the build
  machines set `JAVA_HOME`, which goes first.
