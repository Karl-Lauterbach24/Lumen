## New in 1.2.0

- **3D files are recognised automatically.** Lumen finds out whether a file is 3D and how the eyes are
  arranged: from what the file says about itself, from the name (`3D`, `SBS`, `H-SBS`, `TAB`, `HOU` …), and by
  comparing the picture halves of a few frames. Half or full resolution follows from the frame size. On a 3D
  output profile the check runs before the file starts, so playback begins in the right format; on a 2D
  profile a 3D file is shown as one eye. *Picture → 3D source* shows what was found and why, and still lets
  you choose by hand.
- **MKV with two views (MVC).** Files made from a Blu-ray 3D that carry both views in one H.264 stream play
  in 3D with both views, on every platform, like the disc itself.
- **Blu-ray 3D decodes on several cores.** The MVC decoder used one core as soon as both views were wanted.
  It now decodes the slices of a picture in parallel (a Blu-ray 3D carries six per picture and view): 263
  picture pairs per second instead of 68 on an Apple M3 Pro for a disc at 36 Mbit/s, 119 with two threads,
  the same pictures bit for bit. The 3D test disc and the frame-sequential output at 120 Hz now play without
  a dropped frame.
- **Fixed: a band of the right eye wrong for a second at a time** in 3D files and discs (present in 1.1.0).
  A slice of the second view whose data ends in a lone stop byte lost that byte in the decoder, which then
  replaced the slice by a copy of the left eye; the fault stayed until the next key picture. In the MVC test
  file this hit 23 of every 138 pictures.
- **Fixed: one eye black for a single picture** after a short group of pictures in a Blu-ray 3D (present in
  1.1.0): the two views left the decoder in different order and were delivered unpaired.
- **Subtitles of 3D files are drawn once per eye.** With side-by-side, top-and-bottom or frame packing
  output, subtitles used to lie across both halves, unreadable in 3D. Lumen now draws them per eye and moves
  them in front of the screen by the profile's subtitle depth (adjustable while playing): text subtitles
  (SRT, ASS, WebVTT …) as well as picture subtitles (PGS, VobSub), which Lumen reads from the file itself.
- **H.264/MVC in MPEG-TS** (both views in one track of a `.m2ts`/`.ts`, e.g. from a 3D camcorder) is
  recognised and decoded in software; before, the hardware decoder failed on every picture and the
  screen stayed black.
- **DCP: keys outside their KDM period.** When all keys of a composition are there but the KDM is expired or
  not yet valid, the Cinema tab shows the period, a short legal notice and a box *I know what I am doing –
  decrypt anyway*; ticked, Lumen decrypts that composition until the program ends. A KDM that ends before a show
  started now would end gets a warning. A second KDM with the same file name (often just `kdm.xml`) used to
  replace the first one on disk; it now gets a number. KDMs load from the ZIP package distributors send (the
  ones for this player's certificate are taken, the others reported) and by dropping files onto the window; a
  KDM for another certificate is named as such at the composition instead of "KDM required". CI decrypts a DCP
  with an expired KDM and reads a KDM package.
- **Screen readers** (VoiceOver, Narrator, Orca) find a name for every button, switch, slider, tab and
  recently played item of the control window; 25 icon and list buttons had none.
- **A file that cannot be played** now says so on the start page ("Playback failed: <file> – file format not
  recognised") instead of only in the status line, and is no longer added to *Recently played*.
- **Scaling and decoding follow the hardware.** New profiles and the *Desktop* preset use scaling quality
  *Automatic*: *fast* on a software renderer, *balanced* on integrated graphics, *high* on a graphics card
  or Apple Silicon. Hardware decoding *Automatic* hands pictures to the renderer directly, copies them when
  a filter computes on the CPU (3D conversion), and stays off where no hardware decoder exists (MVC).
- **Playback adapts when frames are lost.** If the machine cannot keep up, Lumen steps down the scaling,
  then relieves the software decoder (skips the deblocking filter, finally leaves out frames so the sound
  stays in sync), and shows in the control window what it took back. What a profile could not manage for a
  kind of material is remembered for two weeks. Can be switched off per profile.
- **No dropped frames at the start, and none while playing.** A file, a DCP or a disc now starts when its
  first picture is on screen instead of dropping the first pictures while the sound already runs. On an Apple M3 Pro, H.264, HEVC
  (10 bit), AV1 and VP9 in 4K at 60 pictures per second, HEVC in 8K, ProRes, interlaced MPEG-2, MVC with both
  views and JPEG 2000 in 2K and 4K played for the length of the test clips without a single dropped frame.
- **JPEG 2000 (DCP) decodes 20 to 28 % faster.** Lumen's FFmpeg runs the inverse wavelet transform over
  neighbouring memory and inlines the arithmetic decoder; the pictures are the same bit for bit. A 4K DCP at
  24 pictures per second now plays at full resolution on an M3 Pro (27 pictures per second at 271 Mbit/s,
  before about 22).
- **DCPs on slower machines keep their resolution longer.** When the CPU cannot decode JPEG 2000 in real
  time, Lumen first leaves out the finest bit planes of every code block – two, then four – before it halves
  the resolution. That doubles and more than triples the decoding speed (2K) while the picture differs from
  the full decode by less than an 8 bit output shows (51 and 46 dB). The level is estimated from bit rate and
  core count when a DCP starts, raised step by step while frames are lost, applied without restarting the
  composition, and remembered for two weeks. Only in *automatic*; *full resolution* decodes everything.
- **Fixed: a few frames lost at every reel change of a DCP.** The decoder now runs ahead in its own thread.
- **The control window opens faster.** Dialogs and the tabs *Cinema*, *Streaming* and *Plugins* are built
  when first opened: 0.75 s instead of 0.91 s from program start to the first picture of a file on an M3 Pro.
  The plugin store is no longer contacted at every start, only when the *Plugins* tab is opened.
- **The embedded player window draws in its own thread** (macOS, and wherever a profile embeds the picture).
  The picture no longer waits for the control window, and frame-sequential 3D reaches the display's rate:
  120 pictures per second on a 120 Hz screen, where it drew 65 to 90 before. That mode also uses the fast
  scaler now, because every picture has only a few milliseconds.
- **A 3D file on a 2D profile starts as one eye** instead of switching after a second: the picture check
  runs while the file loads.
- **Fixed: playback stayed at 0:00 with bitstream sound** when the audio device does not take the bitstream
  (a Mac's speakers, most headphones). mpv fell back to decoding but never started the sound; 1.1.0 and
  stock mpv 0.41 do the same. This hit the supplied preset *1080p DLP 3D projector* on a machine without
  a receiver.
- **New logo:** an eye with a disc for an iris.
- **Automatic deinterlacing** for DVDs and 1080i material; the switch in the *Picture* tab now forces it.
- **Fixed: crash when opening a Blu-ray.** The disc overview, the disc navigation and the player could open
  discs at the same moment; libbluray then freed the same memory twice.
- **Fixed:** a message about a missing Vulkan library was shown as a playback error on macOS.
- Lumen's own window falls back to mpv's older renderer if the new one cannot start.
- All new texts are translated into the 16 interface languages.

## Notes

- **The frame counts above come from one Apple M3 Pro** and from clips of 12 to 40 seconds made from one source
  (upscaled to 4K and 8K), in the embedded player window. JPEG 2000 at 48 pictures per second (3D DCP, 2K)
  played without a dropped frame at 249 and at 281 Mbit/s; the decoder alone reaches 73 and 64 pictures per
  second there. At 403 Mbit/s, more than a DCP may carry, it reached 46.
- **Other machines were not measured as players.** The CI machines (virtual, 3 or 4 cores, no graphics card;
  Windows, macOS and Linux on x86-64 and ARM64) now print how fast the software decoder alone runs on
  generated clips (`tools/bench_decode.sh`, in the log of the Blu-ray 3D test). That is a lower bound for
  small machines, not a statement about any real one. On those 3 or 4 cores, H.264 at Blu-ray bit rate ran
  at 3.4 to 6.4 times real time, H.264 in 4K at 1.3 to 2.4 times, interlaced MPEG-2 at 17 times and more.
  **JPEG 2000 does not reach real time there at full precision:** a 2K DCP at 241 Mbit/s decoded at 7 to 14
  pictures per second instead of 24 (the M3 Pro with 12 cores: 42). With four bit planes left out the same
  machines reach 20 to 42 – real time or close to it at full resolution – and a 4K DCP at half resolution
  with four planes left out 11 to 35 (one Intel machine only 4). So a machine with four cores should play a
  2K DCP at full bit rate with the automatic levels, some of them only at half resolution; this was not
  tried in the player on such a machine.
- **Frame-sequential 3D at 120 Hz was measured on the Mac's own 120 Hz panel only.** There the window is
  drawn 118 to 120 times a second and no picture was dropped in 33 seconds, with a side-by-side file, an MVC
  file and the Blu-ray 3D image; mpv counted one to three late pictures per run. A late picture swaps the eyes for
  shutter glasses. No 120 Hz projector was available, so how this behaves on a real 3D display is not known.
- **The MVC fixes were found and checked with three streams** (two Blu-ray 3D images, one MKV). Slice
  threading only helps where a picture has several slices – Blu-ray requires that; a file encoded with one
  slice per picture decodes on one core as before. With slice threads FFmpeg conceals no errors: on a damaged
  disc a broken slice of the second view is still replaced by the first view's picture, but other damage
  stays visible until the next key picture instead of being smoothed over (tried with a stream damaged on
  purpose). There is no CI test
  for the two faults, because no MVC encoder is available to make a test stream.
- **Leaving out bit planes was measured, not judged by eye on a cinema screen.** The numbers (51 dB, 46 dB)
  compare against the full decode after conversion to 8 bit RGB, for one clip in 2K and one in 4K. The
  automatic levels were tried on the M3 Pro with the decoder limited to one, two and three threads, not on a
  machine that is slow by itself.
- **Per-eye text subtitles of 3D files are plain text:** bottom centre, one style; italics, colours and
  positions from the subtitle file are not kept. Picture subtitles keep their look and position, but only
  for local files (the track is read a second time) – a 3D stream from the network still shows them once
  over the whole picture. Tried with one half side-by-side file and its PGS track (side-by-side and
  top-and-bottom output, a start in the middle, jumps back and forth, subtitle delay) and with a loaded
  .sup file next to an MVC stream; CI reads a generated PGS file on every platform.
- **Tested on one machine with a handful of files.** The 3D detection was run against one half side-by-side
  clip, one MVC MKV and one Blu-ray 3D image on an Apple Silicon Mac, and in CI against generated clips (two
  shifted views side by side and on top of each other) and 2D pictures that must not pass (colour bars, test
  cards, letterboxed and fractal pictures). No real top-and-bottom film, no file with 3D metadata in the
  container and no 3D display were available.
- **Which eye comes first is not detected.** Left is assumed unless the file name says `RL`. Anaglyph and
  checkerboard files are not recognised.
- **The hardware classes come from the driver's name.** Windows and Linux machines, integrated graphics and
  software renderers were not tried on real hardware; only the classification of their driver names and the
  rules that follow from it are tested. The runtime adaptation was provoked with an 8K 60 fps file on the
  same Mac; its rules are tested with simulated counters.
- The fallback to mpv's older renderer could not be tried: none of the test machines fails to start the new one.
- Skipping the deblocking filter shows as blocks in low-bitrate video. It only happens when frames are being
  lost; *Adapt performance automatically* in the profile switches it off.
- The notes of 1.1.0 about casting, frame-sequential 3D, the TV apps, code signing and untested hardware
  still apply.
