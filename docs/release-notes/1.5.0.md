`SHA256SUMS.txt` lists the checksums of the packages; each image has its own `.sha256` beside it.
Linux: `sudo apt install ./Lumen-….deb` or `sudo dnf install ./Lumen-….rpm`. `LumenOS-update-1.5.0.zip`
holds the two Debian packages and their checksums, for updating a LumenOS device from a USB stick.


## New: LumenOS – Lumen as a player of its own

A small Debian 13 system that starts straight into Lumen on the television and is operated from the
sofa. Write the image to a USB stick, start the machine from it, and the first start leads through a
setup. [os/README.md](https://github.com/Karl-Lauterbach24/Lumen/blob/main/os/README.md) has all of it;
in short:

- **Setup, in 16 languages:** the language; a remote, if one is connected; *Install on this device*
  (puts LumenOS on a disk of the machine – the setup goes on there after the restart) or trying it from
  the stick; the network; an update; and what the device gets for encrypted discs.
- **Remotes and gamepads** – USB, Bluetooth, infrared, the television's own remote through HDMI-CEC:
  when a device appears that Lumen does not know, it asks for its buttons – *press the button for Up* –
  six that are needed and thirteen that can be skipped, and from then on the device just works.
  Keyboard and mouse need no setup.
- **Discs** from any drive the kernel knows (SATA, USB) are mounted when inserted and play with their
  menu; **films** from the internal disk, from USB storage and from SMB and NFS shares.
- **Encrypted discs are a decision of the user,** made in the setup or under *Settings › Discs* with
  three switches that are off until they are turned on:
  - *Blu-ray: key database* – the database its community keeps, for Debian's `libaacs`. The image carries
    it as it was on the day the image was made; switched on, it is put in place and refreshed once a
    week when there is a network.
  - *DVD: libdvdcss* – carried in the image as a package that is not installed (built with Debian's
    `libdvd-pkg` while the image is made); switched on, it is installed from there.
  - *MakeMKV*, for playing and for **copying discs** to the internal disk, a USB disk or a share.
    MakeMKV's licence does not allow passing it on, so it is not in the image: after the page with its
    licence it is loaded from makemkv.com and built on the device.

  Nothing restarts for any of them. The repository holds none of this – only the images do, and
  `LUMENOS_NO_KEYDB=1` / `LUMENOS_NO_DVDCSS=1` build an image without.
- **Keeps itself up to date:** every six hours, and in the setup, LumenOS asks GitHub for the latest
  release, loads the package for its machine, checks it against `SHA256SUMS.txt`, waits until nothing is
  playing, copying or being set up, and installs it.
- **Updates without a network,** from the top folder of a USB stick – it is offered as soon as the stick
  is plugged in: the package `Lumen-…-linux-….deb`, `LumenOS-update-….zip`, or **the source code as
  GitHub hands it out** (*Code › Download ZIP*). The source code cannot replace the compiled core of the
  player; what it brings is the interface, the translations, the icons and LumenOS's own scripts, laid
  over those of the installed package until the next package replaces both. A zip that asks more of the
  core than the installed one has is refused, with the note that a package is needed.
- **A drive or a share that stops answering does not stop the interface.** It is left out of the
  library after six seconds and comes back by itself when it answers again. A disc that leaves the
  drive while it plays ends the playback.
- **A machine without a graphics driver** (a virtual machine, a board Mesa has no driver for) gets the
  interface from Qt's software renderer instead of OpenGL computed by the processor. With the latter a
  single new picture – the clock, a disc that had left the drive – reached the screen only together
  with the next one.

## Fixed

- **Linux: an empty drive was shown as holding a Blu-ray.** The kernel reports a placeholder size for a
  drive without a disc; Lumen now asks the drive itself.
- **Linux, Wayland: 16-bit colour.** Without being told otherwise Qt takes the first display format the
  graphics driver offers, and that can be RGB565 – seen with Mesa's software renderer. Gradients then
  show rings, in the interface and, in Lumen's own player window, in the picture of the film. Lumen now
  asks for eight bits per colour.
- **A machine without VA-API or VDPAU showed a red error line** after every start of playback
  (`vaapi: libva: vaGetDriverNames() failed`). mpv then decodes in software and nothing is wrong; the
  message is no longer shown as an error.
- **Lumen's own player window started with a visible mouse pointer** when the window appeared under
  the pointer. It appears when the mouse moves, as before.
- **Recently played: a disc was listed under the folder it was mounted in** when it carries no name of
  its own; the name of its volume is used.

## For developers

- `lumen --os` (or `LUMEN_OS=1`) starts the interface for the television: `qml/Os*.qml`,
  `src/OsBridge` (storage, the bridge to the system), `src/InputMapper` (evdev devices, the wizard),
  `src/RipManager` (MakeMKV). `LUMEN_OS_WINDOWED=1` keeps it in a window on a development machine,
  `LUMEN_OS_ADMIN=tools/mock_lumenos_admin.sh` stands in for the system helper, and
  `LUMEN_OS_SCRIPT="key down; key ok; fake Pad; btn Pad 1; snap page.png; quit"` drives it without hands.
- Everything LumenOS adds to Debian comes out of Lumen's package (`share/lumen/os`, from `os/system`), so
  an update of Lumen updates the system's part: the session (`cage` with Lumen in it), the one helper
  Lumen may call with the system's rights (`lumenos-admin`, one `sudo` rule), the updater, the offline
  updater, mounting of discs and storage, the installer. `os/image/build.sh <amd64|arm64> <package> <out>`
  builds an image with live-build.
- `os/system/API` and `OsBridge::kApi` say what the interface asks of the core; a source zip is only
  taken as an overlay (`/var/lib/lumenos/overlay`) when its number is not higher.
- `tests/os_test.cpp`: the button wizard (required and optional steps, a button that is already taken, a
  setup that is broken off), stored assignments, and copying with a stand-in for `makemkvcon` (progress
  lines, the folder a copy goes to, a copy that fails).
- The stand-in for libdvdcss looks for the library again at every open as long as it has not found one.
- `LUMEN_DEFAULT_FORMAT=1` lets Qt choose the display format as up to 1.4.1 (for comparison).

## Checked, and known limits

Checked on an ARM64 virtual machine (QEMU with KVM, software rendering), from the image:

- start from the stick; the setup with the keyboard; a simulated USB remote: found, its six buttons asked
  for and stored, and used afterwards – also on the installed system, to which the assignment went along;
- installing to a disk, starting from that disk, the setup going on there;
- the update against GitHub ("up to date") and against a stand-in release server: a newer package is
  loaded, a package that does not match its checksum is refused, and an update that arrives while a disc
  plays waits and installs after the disc is stopped;
- the three updates from a USB stick – package, update zip, source zip (the interface then showed the
  changed text from the zip, and a package installed afterwards took the overlay away again);
- the key database (loaded, 188 026 entries, weekly timer on) and libdvdcss (installed from the image,
  loaded by Lumen for a DVD);
- a Blu-ray image and a DVD image in the virtual drive: mounted, played on inserting, stopped with Esc,
  ejected from the interface, and pulled out while playing;
- a USB stick with a film; an NFS share with films, its server switched off under it (the share left the
  library, the interface stayed usable) and on again (it came back);
- the mouse pointer: none at rest, there when the mouse moves;
- the picture keeping up by itself: the clock in the corner followed the time over several minutes,
  before and after a disc had played, and the start page changed when the disc left the drive. (This
  is where the software renderer above came from. With it, on this virtual display, a single change
  could still stay unseen until the next one; a dot in the corner that changes its colour unnoticeably
  once a second – only without a graphics driver – brings it out. Why the display held it back was
  not found: Qt had handed the picture over and the compositor had confirmed it.)

Checked with the x86-64 image on an emulated PC (QEMU without hardware acceleration, so slowly):
starting from the stick, installing to a disk and starting from that disk – each once with UEFI and
once with a BIOS – and the setup going on from the disk and asking GitHub for an update.

Not checked, or with limits:

- **No real hardware.** No television, no real remote, no real disc drive: the USB Blu-ray drive at hand
  had stopped answering again (see the notes of 1.4.1) and could not be handed to the virtual machine.
  Sound was not listened to.
- **Wi-Fi, Bluetooth and HDMI-CEC** could not be tried – the virtual machine has none of them. The pages
  for them call NetworkManager, BlueZ and `cec-ctl`; a Wi-Fi password is typed with the on-screen
  keyboard.
- **MakeMKV was not set up in the test** (that accepts its licence, which is the user's to do), so
  copying a disc on the device ran only against a stand-in for `makemkvcon` (`tests/os_test.cpp`).
- **An encrypted disc was not played.** The key database and libdvdcss were put in place and loaded;
  that a given disc opens with them was not tried.
- **SMB shares** go the same way as NFS shares but were not mounted in the test.
- **ARM:** the image starts on machines with UEFI firmware (servers, many boards with EDK2 or U-Boot's
  UEFI, virtual machines). A Raspberry Pi needs UEFI firmware on its card; there is no image for the
  Pi's own boot chain.
- **Picture:** SDR, through Lumen's own window; HDR is not passed through. Hardware decoding depends on
  the VA-API driver of the machine; without one mpv decodes in software.
- A disc left in its menu counts as playing: an update waits for it (up to 35 minutes per attempt, then
  again at the next).
- Reading ahead of a disc (1.4.1) covers Blu-rays; **DVD** plays with the small buffer it always had.
- Bluetooth devices that want a number typed for pairing (keyboards) are not handled.
- Windows and macOS: built and run through the tests on the build machines; nothing in this release
  changes how they play.
