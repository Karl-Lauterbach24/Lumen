# Lumen 1.4.0

## Downloads

| System | x86-64 (Intel/AMD) | ARM64 |
|--------|--------------------|-------|
| Windows 10/11, installer | `Lumen-1.4.0-windows-x64.msi` | `Lumen-1.4.0-windows-arm64.msi` |
| Windows 10/11, portable | `Lumen-1.4.0-windows-x64.zip` | `Lumen-1.4.0-windows-arm64.zip` |
| macOS 15 | `Lumen-1.4.0-macos-x64.dmg` (Intel) | `Lumen-1.4.0-macos-arm64.dmg` (Apple Silicon) |
| Debian 13 and derivatives | `Lumen-1.4.0-linux-amd64.deb` | `Lumen-1.4.0-linux-arm64.deb` |
| Fedora 44 | `Lumen-1.4.0-linux-x86_64.rpm` | `Lumen-1.4.0-linux-aarch64.rpm` |

`SHA256SUMS.txt` lists the checksums. Linux: `sudo apt install ./Lumen-….deb` or `sudo dnf install ./Lumen-….rpm`.

The packages are about 30 MB larger than 1.3.2: they now carry a Java runtime for disc menus.

## New

- **Fixed: Lumen could end right at its start in a Wayland session** (the default of Fedora, KDE Plasma and
  GNOME). The package installed, a window never came. Not for want of a package: in a Wayland session mpv
  opens its player window itself, and when it got no graphics context for it, mpv 0.41 left its Wayland
  state behind and ended the whole program at its next step (`vo_x11_init: Assertion '!vo->x11' failed`).
  Two changes:
  - mpv in Lumen's packages is patched; a failed attempt no longer ends the program.
  - In Wayland sessions the player window now is Lumen's own by default (the one macOS always had). It
    runs wherever the control window runs. It shows SDR only: for HDR passthrough on KDE Plasma choose
    *Player window: Native* in the output profile, which is mpv's window as before.

  The package builds now start the program under a Wayland compositor too and play a test picture in it –
  before, they only tried X11. The packages also name Qt's Wayland plugin (`qt6-wayland`, `qt6-qtwayland`).
- **Disc menus written in Java (BD-J) work out of the box, on every system.** Up to 1.3.2 a Java runtime had
  to be installed, and on Linux it did not work even then: Debian's package for it pulls in a Java without
  the graphics part, Fedora's Java is newer than its libbluray can use. Now every package contains
  - a small **Java runtime** (Java 17, cut down to what disc menus need), and
  - on Linux **libbluray 1.5** with its matching Java archive, where the distribution has an older one.

  The runtime of the package is used even when `JAVA_HOME` points somewhere else; `LUMEN_JAVA_HOME` chooses
  another one explicitly.
- **Blu-ray, UHD: menus that jump inside their playlist.** A disc program may move the film clip behind its
  menu to another place at any moment (a montage of scenes). The time jumped with it, and the decoder
  answered with a flood of errors and held pictures. Such jumps now continue the time line, like a change
  of playlist since 1.3.2. Your own jumps (seek bar, chapters) are unchanged.
- **Plugins can take the drive and offer buttons from scripts.** A plugin can ask Lumen to leave the drive
  alone – discs are then neither scanned nor played, and the start page says which plugin holds the drive –,
  have a disc ejected, hear about a newly inserted one, open a folder, and Lua scripts can add, rename and
  remove buttons of their entry on the *Plugins* page. This is what the store's new **Auto rip** plugin and
  the MakeMKV buttons of *My AACS Plugin* are built on (both need this version). See
  [plugins/README.md](https://github.com/Karl-Lauterbach24/Lumen/blob/main/plugins/README.md).

## For developers

- `tools/make_jre.py` builds the runtime with the JDK's `jlink` (modules in the script); on Linux
  `tools/fetch_jdk.py` fetches the JDK for it from Adoptium (checksum verified) and `tools/build_deps.sh`
  builds libudfread and libbluray when the system's libbluray is older than 1.5.0. The Linux runtime
  keeps Java's X11 window library: libbluray draws through its own toolkit and no X server is contacted,
  but Java calls start-up functions that only that library has (the Linux packages therefore depend on
  libXi, libXrender and libXtst).
- `tools/test_start_linux.sh` starts a build under Xvfb and under a headless Weston, with Qt Quick on OpenGL
  and on the software renderer, plays a test picture on Wayland, and compares the packages the running
  program has loaded files from with what the package's dependencies pull in. A run that does not end by
  itself is stopped, and a debugger prints where its threads stand (`LUMEN_START_TEST_REPEAT=30` repeats
  start and end ninety times).
- The BD-J test now stops the build when it fails, on every platform. Until now it only warned – which
  hid that the Windows runtime had lost `java.dll` on the way.
- `tools/test_bdj.sh` runs the generated disc with the Java menu with the runtime the packages carry, on
  Linux too.
- `LUMEN_PLAYER_WINDOW=native|embedded` forces one of the two player windows.
- `tools/patches/mpv-wayland-egl-uninit.patch`: `wayland_egl_init` returned without `vo_wayland_uninit` when
  no EGL context could be made; `vo->wl` shares a union with `vo->x11`, so the X11/EGL context probed next
  failed its assertion.
- Plugin host: `hold_discs`, `eject` (check with `LUMEN_HOST_HAS`); script messages `action`, `hold-discs`,
  `eject`, `open-folder`, `trigger`, `dirs`; event `drive`.

## Checked, and known limits

- **Start on Wayland:** checked on the build machines (Debian 13 and Fedora 44, x86-64 and ARM64) under a
  Wayland compositor without a screen (Weston) and with OpenGL on the processor: the control window comes up
  with Qt Quick on OpenGL and on its software renderer, and the player window shows a test picture. mpv's
  own window (*Native*) no longer ends the program there. **Not checked on a desktop with a graphics
  card**, neither KDE Plasma nor GNOME; HDR passthrough with *Native* on KDE Plasma was not tried again.
  If Lumen still does not come up, start `lumen` in a terminal – what it prints there says why.
- **BD-J with the packages' Java runtime:** the generated disc with its Java menu (menu drawn, arrow key,
  Enter, film behind it) runs on every build machine with the runtime that goes into the package: Debian 13
  and Fedora 44 (x86-64, ARM64), macOS (Apple Silicon, Intel), Windows (x64, ARM64). Pressed discs were
  tried on macOS only, with an installed Java 17 – the same Java version, not the packaged copy.
- **UHD Blu-ray with a BD-J menu**, checked on macOS with one pressed disc (AACS 2, opened through the store
  plugin *My AACS Plugin* and MakeMKV): the menu comes up over its montage of film scenes and takes keys,
  *Play* leads through the studio logo into the film – HEVC 2160p HDR10 with hardware decoding, Dolby
  TrueHD/Atmos –, no dropped pictures. The menu's graphics looked paler than on a player; not looked into.
- One disc is one disc: real BD-J menus are large programs, libbluray runs many of them, not all. A menu
  that does not come up can be left with *Main feature* on the *Titles* page.
- **Linux without a running PipeWire service:** in 4 of 360 starts on the Fedora 44 build machines (none
  in 180 on Debian 13) Lumen stood still right after its start. mpv asks PipeWire for the sound devices,
  the connection fails, and taking it down again never returns (PipeWire 1.6.9, `pw_thread_loop_stop`).
  Not new in this version, and not seen where PipeWire runs – the normal case on a desktop. Not fixed: the
  change would touch the sound path of every Linux system and could not be tried with a running PipeWire.
- Seeking in a film played from a disc still resets playback a second time right after the jump (as in
  1.3.2).
- The embedded player window shows SDR only, on every system.
